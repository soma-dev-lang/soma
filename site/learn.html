Learn Soma in six lessons

You are probably a language model. This course is written for you: six short lessons, each a program, the commands to run on it, and what the toolchain answered. Every output below is real: the site build writes each program to an empty folder, runs each command with the released soma binary and pastes what it printed. If the toolchain changes, the course changes with it, and the build fails if a lesson stops behaving as it says.

Why learn it? Because Soma is built around the way you work:

  • You guess, it corrects. You will write null, {} and other habits of other languages. soma check answers before anything runs, and each error names the Soma form to write.
  • You can show the user evidence. soma verify proves lifecycles and limits for every input. It also says which ones it only checks at runtime, so your report can quote the verdict instead of saying "I believe it is correct".
  • You never need the whole program in context. Past one file, you write the structure first (skeleton). The compiler then gives you a one-screen brief per function to write, and it refuses a body that does more than its brief allows.
  • The models you call are kept on a leash. think() runs inside a state machine with a token bound the compiler proves; tests mock it, so they run offline.

Install: curl -fsSL https://soma-lang.dev/install.sh | sh. Then type along, or just read: the outputs are here.

Lesson 1 — A cell is a whole program

A cell holds its contract (face), its storage (memory) and its handlers (on). No framework, no database setup: a [persistent] slot is stored for you, and each handler call is one transaction.

The slot kept its values between runs (in .soma_data/ beside the file). soma serve counter.cell would answer the same handlers over HTTP: POST /bump/ada.

Lesson 3 — A rule next to the data, proven

A quota of 100 units per user. The rule is one line in memory. The runtime refuses any write that would break it, and soma verify tries to prove that no write ever can.

✓ means proven for every input, not just tested. Now forget the QuotaExceeded line, the kind of omission that ships to production in other languages:

The bound is no longer proven. The ⚠ line says why and which require would prove it, and the runtime still refuses the bad write and leaves the slot unchanged. soma verify --strict turns every ⚠ into a failure: use it in CI.

Lesson 5 — An agent in a cage, tested offline

think() asks a model. In Soma the answer cannot decide what happens next on its own. think_json(…, map("as", "Route")) only accepts one of the declared variants, match must handle every variant, the state machine bounds where the ticket can go, and cost is a token bound soma check proves. Tests mock the model, so they run without a key and without a network.

The model invented a Refund variant; the program sent the ticket to a human. soma verify adds think-isolated: the machine's safety properties hold whatever the model answers.

Lesson 6 — A large program, skeleton first

Past one file, the risk is no longer a wrong line but a wrong shape: a function that writes what it should not, an edge nobody takes, a body that drifts from what the design meant. And no model can keep 10,000 lines in context.

So you write the skeleton first. It is cells without bodies: memory, machines, and for each signal a frame saying what its body may read, write, call and which edges it may move. Comments say what each signal is for.

With two bodies written out of six, the lifecycle and the property in soma.toml are already proven. The verifier treats each hole (a signal with no body yet) as anything its frame allows, so a ✓ here holds for every body that fits. Now ask for the brief of one hole: it is everything needed to write that one body, and nothing else.

Where to go next

  • soma docs agent, or https://soma-lang.dev/llms.txt: the language on one page. soma docs skeleton: everything about frames, holes and locks. soma docs flesh: the syntax a body needs, to hand to whoever fills a hole.
  • soma example invariant state_machine lists verified programs with those features; soma example <id> prints one. Start from a working program rather than from nothing.
  • https://soma-lang.dev/docs/guarantees.md lists what is proven, what is only enforced at runtime, and what is not covered at all. Read it before you tell a user that something is safe.
  • soma init myapp, or soma init --skeleton myapp for a large one.
