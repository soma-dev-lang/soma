# Soma — the law: business rules outside the code

`soma verify` proves the flesh keeps to the skeleton. It proves nothing about
whether the program does what the business requires, unless something says
what the business requires. That is the law.

Three artefacts, three reviewers:

    law       entities, states, actions, rules   the person who owns the rules
    skeleton  memory, state machines, frames     the architect
    flesh     the code                           you

The law is written first, outside the code, and locked. The code is aligned
on the law — never the reverse. You do not edit a `.law` file or `law.lock`.

## The law: a file that names no code

```
// lois/sanctions.law
law Sanctions

entity Holder "Whoever holds units of the fund, on its register."
term   Report "A declaration made to the regulator."

state  frozen(Holder): Bool "The holder is under an asset freeze."
state  paid_to(Holder): Int "What the fund has paid the holder, in cents."

action Payment(h: Holder, n: Int) "Cash paid by the fund to a holder: a redemption, an indemnity."
action Freeze(h: Holder)          "The holder is placed under an asset freeze."

rule "SAN-02" "No payment to a frozen holder"
    about    Payment, Holder
    source   "Regulation (EU) 269/2014, art. 2"
    owner    "compliance"
    requires Payment(h, n): not frozen(h)

rule "SAN-05" "A payment above the threshold is reported before it is made"
    about    Payment, Report
    source   "Internal procedure 7"
    owner    "compliance"
```

A law declares, in this order:

- `entity Name "definition"` — what the rules are about;
- `term Name "definition"` — a word of the business a rule in a sentence speaks of;
- `state name(Entity): Bool | Int "definition"` — a fact a rule reads, about one entity;
- `action Name(p: Entity, n: Int) "definition"` — what happens;
- `rule "ID" "sentence"`, and under it `about` (the actions, entities or
  terms it speaks of — each must be declared), `source`, `owner`, and its
  formal reading when it has one: `requires Action(params): condition`
  (when the action is allowed) or `always p: condition` (what holds of
  every entity).

"SAN-02" has a formal reading: its refusal is derived, nobody writes it.
"SAN-05" stays a sentence: the code serves it and says where. A cell, a
handler or a test named in a law is refused (E0123). `//` starts a comment.

The program says which laws it is under, in soma.toml:

```
[law]
files = ["lois/sanctions.law"]
```

## A rule with a formal reading: the guard is derived

When a rule can be said formally, the owner of the law says it, and the
refusal is not yours to write:

```
rule "SAN-02" "No payment to a frozen holder"
    about    Payment, Holder
    requires Payment(h, n): not frozen(h)
```

A condition is `not`, `and`, `or`, parentheses, a state of a parameter, and
a comparison between an Int state or an Int parameter and a number or a
parameter. No arithmetic, no call, no quantifier (E0132): its owner reads it.

The skeleton says how the program corresponds:

```soma
skeleton Fund {
    memory {
        paid:   Map<String, Int>    [persistent]
        status: Map<String, String> [persistent]
    }

    maps frozen(h) = (status.get(h) ?? "valid") == "frozen"

    face {
        signal redeem(holder: String, n: Int) -> Int
            writes paid
            realizes Payment(holder, n)
        signal freeze(holder: String) -> String
            writes status
            realizes Freeze(holder)
        signal purge() -> Int
            writes paid
            silent "removes zero balances; no holder's state changes"
    }
}
```

- `maps state(p) = expression` — a clause of a skeleton: one state of the
  law, read from the program. Pure, at the type the law declares, once per
  program. It may read the slots and machines of its cell, and another
  cell (or its own) through a signal whose frame changes nothing:
  `maps frozen(h) = Register.state_of(h) == "frozen"`.
- `realizes Action(args)` — the signal IS that action. An argument is a
  parameter of the signal, a literal, or what a slot of the cell holds for
  a parameter: `realizes Payment(o via holder_of, n)`, the holder of order `o`.
- `silent "why"` — the signal writes under the law and is no action of it.

What follows, and what you do NOT do:

- **The guard is derived.** For `redeem`, the rule gives `not frozen(holder)`,
  judged before the body runs, outside its frame. A refused call fails with
  kind `law`, the rule, its sentence and its source in the message, and
  writes nothing. Do not write that `require`, and do not test for it in
  the body: the brief of the signal shows it (`law "SAN-02" …`).
- **A refusal names every rule the call breaks**, in the order of the law:
  `refused by the law — rule "A" (…): it requires …; rule "B" (…): it
  requires …`. A test of one rule (`matching "B"`) does not need a state
  where it is the only one broken.
- **A state that cannot be read is not a refusal.** A `maps` may read
  through a signal; while that signal has no body, the guard judges
  nothing: the call fails with kind `not_implemented` and names the state
  and the hole, not the rule. `soma check` warns at the `maps`, and `soma
  law` shows the rule as `checked (derived, awaiting Cell.signal)`. A
  `maps` that reads the memory directly is judged on the bare skeleton.
- **A `maps` is read as a body.** A field that does not exist, `get_status(x)
  == Variant`, a literal of the wrong type passed to `Other.signal(…)`, a
  signal of another cell whose frame writes: `soma check` says each at the
  `maps` (warnings in this edition, errors in the next). And when the
  program declares a type named like an entity of the law (`cell type
  Invoice = String`), a parameter bound to that entity by `realizes` must
  have it — `realizes Payment(account, n)` on an `Account` is said.
- **A refusal tagged by hand no longer serves a formal rule.** `soma law`
  says `served Fund.redeem (derived)`.
- **A signal that writes what a `maps` reads owes a binding** (E0138): it
  `realizes` an action or is `silent`. This is judged on the frames, before
  any body exists — a second way to pay cannot be added without the law
  knowing.
- **A state a rule needs must be mapped** (E0136): the message gives the
  line `maps …` to write.
- A test `under` a formal rule holds an `assert_fails … matching "SAN-02"`.

`soma law app.cell --map` prints the correspondence for the owner of the
law: each state and its `maps`, each action and its signals, each `silent`
signal and its reason.

**Map the states your actions change.** The closure sees a signal through
what it writes: only a slot (or a machine) that some `maps` reads is under
the law. If the law says nothing of what a payment changes, a second
signal that pays is not seen. Ask the owner for the state — `state
paid_to(Holder): Int` — and map it (`maps paid_to(h) = paid.get(h) ?? 0`).

Limits, stated: a guard is a precondition of ONE call — a signal that
performs the action for many entities at once (a batch) has no formal
reading, and its rule stays a sentence served `under`. A rule kept by
something other than a refusal (an order recorded then rejected) needs the
law to name the action that is refused. `silent` is declared and reviewed,
not proven.

## A rule that stays a sentence: served in the code

A rule with no formal reading — a consequence, a batch, a deadline — is
served by the bodies, and each place says so:

```
skeleton Fund {
    face {
        signal redeem(holder: String, n: Int) -> Int
            reads reported
            writes paid
            realizes Payment(holder, n)       // an action: SAN-02 is derived
        signal fees(holder: String, n: Int) -> Int
            writes paid
            realizes Payment(holder, n)
            exempt "SAN-05" "management fees are capped far below the threshold"
    }
}
flesh Fund {
    on redeem(holder, n) {
        require n < 1000000 || (reported.get(holder) ?? false) else NotReported "{holder}: report first" under "SAN-05"
        …
    }
}
cell test LargePaymentIsReported under "SAN-05" {
    rules { … assert_fails Fund.redeem("a", 2000000) matching "NotReported" }
}
```

- `realizes Action(args)` or `realizes Term` — a clause of a signal, in the
  skeleton: this signal is that action, or an instance of that term. When you add a signal, ask
  which term it realizes: that is what lets the check tell you which rules
  it owes.
- `under "ID"` serves a rule, in three ways, from the strongest:
  - on a frame that has a guarded edge (`moves a -> b when Other.state`):
    **proved** on every path;
  - at the end of a `require … else Tag "…"` (same line): **checked** at
    run time. A helper of the cell that the handler calls counts;
  - as a statement of its own, in the branch that handles the case — an
    order recorded then rejected, a share withheld while the others are
    paid: **handled**. Nothing checks the branch does what the rule says;
    only its tests do. Prefer a refusal when the case can be refused.
- `exempt "ID" "why"` — a clause of a signal: the rule does not apply to
  it. The reason is required and is read by a reviewer.
- `cell test Name under "ID", "ID2" { … }` — the tests that show a rule at
  work. They may be in another `.cell` file beside soma.toml, or in `tests/`.

Without a `[law]` table these clauses are accepted and do nothing.

## What always holds: the monitor, and the gesture of refutation

`requires` says when an action is allowed. A rule may also say what holds
of every entity, in every state:

```
rule "RMB-01" "The total refunded on a payment never exceeds the total captured"
    about  Refund, Payment
    always p: refunded(p) <= captured(p)
```

Its **monitor** is derived from that line and from the `maps` of its
states. Nobody writes it — so nobody, and no agent, can write a lenient
one. `soma monitor app.cell "RMB-01"` prints it; `soma law` says the rule is
`monitored`, and for a rule with no `always`, that it has no monitor.

```
soma fingerprint app.cell                    # one sha256 per law, skeleton, flesh (by tokens), manifest, binary — and the program
soma refute app.cell --trace t.trace         # play a trace from an empty state; judge every monitor after each call
soma refute app.cell --trace t.trace --expect <program fingerprint>
soma attack app.cell "RMB-01" --depth 3      # search small traces for one that refutes; finding none proves nothing
```

A trace is calls and nothing else — one `Cell.signal("literal", 42)` per
line; no `assert`, no expression. `soma refute` answers one of four
verdicts, each with its exit status, and names the program by its
fingerprint:

    holds     0   every call was played, no monitor failed (on THIS trace: nothing is proven)
    refuted   1   a monitor fails after an accepted call: the rule, the step, the values
    rejected  2   the program refused a call: the trace proves nothing
    mismatch  3   this is not the program the trace aimed at (`--expect`)

`refuted` is not `rejected`: a counter-example that the program now
refuses is no longer one. A trace kept in `refutations/*.trace` is
replayed by `soma law`: while it refutes, the rule's status is `refuted`;
once the body is corrected it is listed as no longer refuting. `soma law`
also runs the tests `under` each rule and says `passes` or `FAILS`.

A program judged by a trace reads nothing of the outside: `refute` and
`attack` refuse one whose handlers call `now()`, `random()`, `think()`,
`http_*` or read a file, and name the handler. Pass what the outside gives
as a parameter of the signal; the trace then gives it.

You do not weaken a monitor, a trace or a test to make the table green:
correct the body.

## What `soma check` refuses

    E0123  a law that is missing or does not read as a law
    E0124  a law that differs from law.lock
    E0125  `under` / `exempt` naming a rule no law declares — you cannot invent a rule
    E0126  `realizes` naming a term no law declares
    E0127  a frame `under` a rule with no guarded edge
    E0128  `exempt` without its reason
    E0129  a rule nothing serves
    E0130  a signal that realizes a term of a rule and neither serves it nor is exempt
    E0132  a condition outside the closed language      E0133  a name the law does not declare
    E0134  a `maps` of an unknown state, or twice       E0135  a `maps` that is not a pure reading
    E0136  a state a rule needs has no `maps`           E0137  `realizes A(args)` that does not fit
    E0138  a write under the law with no binding        E0139  `silent` without a reason
    E0140  a law the lock holds, dropped from soma.toml
    W0020  a rule that is served but has no test; a `maps` that reads through a signal with no body yet

E0130 is the forgotten path: a second way to pay, written later, that omits
the check. Its message is the instruction:

```
error: the rule "SAN-05" (A payment above the threshold is reported before
it is made — Internal procedure 7) is not served in `Fund.indemnify`, which
realizes `Payment` — add a refusal `under "SAN-05"` to its handler (or the
statement `under "SAN-05"` in the branch that handles the case), or `exempt
"SAN-05" "<why it does not apply>"` to its signal
```

**On a skeleton, a hole owes; it has forgotten nothing.** While the signal
has no body, the same rule is not an error: it is an open obligation of the
flesh, counted (`○ 12 rules of the law still owed by the flesh`), listed by
`soma law --todo` (`Fund.indemnify owes "SAN-05"`) and shown in the brief
of the hole (`owes "SAN-05" …`). So a skeleton under a law in sentences
checks, and `soma verify`, `soma test`, `soma refute` and `soma attack` run
on it before any body exists — `VERIFY OK (skeleton — the holes above are
open obligations, and 12 rules of the law still owed by the flesh)`. The
day the body is written without serving the rule, E0130 is back.

## `soma law`

```
soma law app.cell             # each rule: source, where it is served and how, its tests, its status
soma law app.cell --todo      # only what fails, as a numbered work list — start here (`soma next` hands them out one at a time)
soma law app.cell "SAN-02"    # one rule: its terms and their definitions, every signal that realizes them
soma law app.cell --json      # the same, for a program
soma law app.cell --map       # the law and the program side by side: states and their maps, actions and their signals
soma law app.cell --lock      # the owner of the law records it as reviewed (law.lock) — not you
```

Status of a rule: `unserved`, `owed` (nothing serves it yet and the signals
that realize its terms have no body), `incomplete` (a signal that realizes
one of its terms does not serve it), `handled`, `checked`, `proved` — the
weakest way it is served anywhere. `soma law` exits 1 while a rule is owed.

For the owner of the law, `soma doctor --program app.cell` (and `hints` in
`soma law --json`) names each state that only `silent` signals change: it
is changed by acts the law does not name. And `soma check` warns when many
`exempt` share their words: an exemption is a judgment on one signal, and a
term that makes many signals owe rules that do not concern them is too
broad — that is said to the owner of the law, not exempted one by one.

`soma docs law --brief` is one screen: what a good law contains. Read it
before writing one. `soma init --law demo` is a whole project to imitate.

## Questions for the owner, and where the owner answers

Some things are decidable on the law and the frames and are NOT tasks for
whoever writes the program. `soma law app.cell --questions` lists them, and
exits 3 while one is open:

- `silent-state:<state>` — a state of the law that only `silent` signals
  change: is one of them a business act the law should name?
- `broad-term:<term>` — a term that three signals or more realize and three
  rules in sentences or more speak of: does each signal owe each rule, or is
  the term to be split?
  (Three and three are a choice, not a measure: no project has told yet
  where a term starts to be too broad.)

The owner answers in the law (name the action, split the term: the question
closes at the next lock), or writes "it is meant" in `decisions.toml`
beside the laws:

```
[[decision]]
question = "silent-state:closed"
answer   = "Closing is bookkeeping: no action of the law."
by       = "finance"
date     = "2026-11-28"
fact     = "Shop.close"
```

`law.lock` holds that file like a law: a decision is not in force until
the lock holds it, and a question reopens when the fact it answered
changes. You do not write a decision and you do not lock: the answer is the
owner's. **Nothing enforces that today**: `soma law --lock` runs for anyone,
so an agent could answer in the owner's name and lock. The file is short
and dated, and a change to it changes the fingerprint of the law — that is
all that makes it visible. Whom a lock belongs to is a proposal (RFC 0005, not
published yet), not decided. While a question is
open, `soma next` does not hand out the rules and the holes that wait for
it; when all that is left waits, it answers `question` and exits 3 — stop,
and report the question.

## When the law is silent or wrong

Do not add a rule in the code, and do not `exempt` a signal to make the
check pass. Say what is missing to the person who owns the law: the rule you
think applies, the signal, and why. A new rule enters the `.law` file, the
law is locked again, and the check then tells you every place that owes it.
